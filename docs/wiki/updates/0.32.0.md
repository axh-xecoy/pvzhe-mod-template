## 发行差异规模

PCK 条目 28,089 → 28,386：新增 643、删除 346、内容变化 1,711。变化集中在 `.godot/exported/gameplay`（1,460 条，多为配置再序列化）、生存配置、投射物配置与关卡配置。条目数量与摘要变化不等于逐个新角色已验收。

## 公开方法的新增可选参数

发行反射（`tools/HostProbe`）确认以下 `TowerDefenseManager` 方法只增加带默认值的参数，旧的“重新编译”源码可继续使用：

- `GetCampFriendly(camp, fliterGraveStone = …, includeUntargetable = …)`：旧两参数调用需重新编译；已编译旧 DLL 的绑定不会自动匹配。
- `BungiSpawn(..., waveOperationId, skipPlacementCheck, spawnSource = null)`：新增 `TowerDefenseCharacter spawnSource`。
- `CharacterDestroy(..., _hitpointScale, brainRetreating = false)`：新增 `Boolean brainRetreating`。

新增 `TowerDefenseManager.GetPacketSlotNum(TowerDefenseLevelSeedBankConfig)`，以及 `TowerDefenseLevelSeedBankConfig.ResolveSlotCount(unlockedSlots, mode, limit)`；后者把“已解锁槽数与模式上限取较小值”的既有规则收进宿主方法。`DragMenuSelectItem` 增加 `_EnterTree/_ExitTree/_Process`，属于选择项生命周期实现，不改变制作配方。模板 C# 不直接调用上述变化方法；示例工程本轮全部对新引用重新编译通过。

## 成员种类变化与旧包重编译

0.32 把部分角色实例的公开字段改成属性：`invincible`、`canBeCollection`、`sleep` 在 0.31 DLL 中没有 `get_/set_` 访问器，0.32 中存在（底层改为新的保护标志）。按 0.30/0.31 编译的旧 pmod 仍用 `ldfld/stfld` 读这些字段，加载后抛 `MissingFieldException`；若 Mod 侧捕获异常只记一条 WARNING，表现是节拍不再推进（发射、伤害、滚动、护具看似失效），场景却照常进入。

这类变化不在方法签名或 `api.json` 里体现，需按发行 DLL 做成员级核对；旧包必须用当前引用重新构建，“能进场景”不能作为兼容依据。

## 发射基准与攻击编辑器

0.32 发行版重新采集原版单发豌豆与普通僵尸：弹速 300（采样位移 130、用时 0.433 秒），配置攻击间隔 1.5 秒，5 次出弹平均约 1.383 秒；0.31 同法约 1.408 秒，差异属采样波动，不能据此断言宿主节奏配置改变。普通僵尸受击矩形随根相对仍为 `(-18,-37,44,70)`，根位置 (860,517)、比例 1、启用状态 true；页面网格起点 (260,75)、9 列 5 行、单元 80×98、植物行内偏移 50。

预设施用的角色场景、AdobeAnimate 资源与玉米投手组件集摘要与 0.31 一致，起点几何沿用不改；`origins.json` 的 verifiedReleases 增加 0.32 组合，并用当前发行重新生成素材会话后 `attack_recipe new-session` 通过。边界：采集只覆盖单发豌豆与普通僵尸参考条件，不覆盖其他弹药、投手优先索敌、穿透/爆炸、暂停与联机；本轮没有在浏览器里确认/采用方案，也没有新 Mod 的战斗发射验收。

## 种植音效与预放置恢复

新增能力键 `plant-placement-audio-v1`（发行 DLL 字面量与源码常量一致）。卡牌配置 `TowerDefensePacketConfig` 增加 `plantAudio`、`plantWaterAudio` 字段，加载器把它们按 `Audio` 前缀纳入 Mod 资源限定；未配置时回退默认种植音效。`XWModPlantPlacementService` 增加内部 `TryPreparePreSpawn(packet, anchor)`：读档/预放置的保存位置按“左侧锚点”还原，列模式下仍只还原一行，并被夹取到别处的 Footprint 会被拒绝。

证据范围：发行 DLL 存在能力键与字段名，源码对应实现可读；本轮未在真实对局验证陆地/水上音效分配、读档还原和拒绝分支，平台差异另行记录。制作入口见 [plant-create](../../../.agents/skills/pvzhe-plant-create/SKILL.md) 与 [卡池](../0.30.0/card-pools.md)。

## 胜利结算的等待条件

`TowerDefenseControlNew` 现在区分 `HasPendingBattleOperations` 与 `HasPendingVictoryOperations`。Mod 关卡胜利发布（`TryPublishResult`/`XWModModeService` 的胜负委托）在 `victory` 时只等待会阻塞结算的操作，失败/中断仍按原战斗操作等待；联机仍要求主机、实例与进程一致。这是“宿主结算前不再被无关战斗操作拖延”的语义修正，不是取消暂停/模态约束。

证据范围：发行 DLL 成员与源码分支静态核对；本轮未构造真实胜利/失败/联机场景重测该等待差异，原有 Mod 关卡胜利运行证据仍属相应版本。

## 载入视图与场景生命周期

`XWModStartupContext` 在实例化 Mod 载入视图时保留 `provider.Scene` 引用并在 `finally` 中 `GC.KeepAlive`，避免实例化期间提供者被重入撤销导致场景资源被提前回收。载入界面相关场景（`Scene/Loading/Loading.tscn`、`Core/SceneManager/SceneLoadeing/*`）与 0.31 摘要一致。制作模式页面/载入视图的流程不变，见 [mode-create](../../../.agents/skills/pvzhe-mode-create/SKILL.md)。
